# teswiz Web API Traffic Capture — Plan & TODO

> Status: **Proposed — awaiting clarifications before implementation.**
> Capture all API traffic (requests and responses) generated by the front-end running
> in the browser, for `PLATFORM=web` (Selenium, Playwright-Java, Playwright-TS).
> On-demand config property, default `false`, with filtering by type / name / domain.

## Goal

For `PLATFORM=web` (so Selenium, Playwright-Java and Playwright-TS), capture all API
traffic (request and response) that the **front-end generates from the browser**. This is
an on-demand config property, default `false`. It must also be filterable by **type**,
**name**, and **domain**.

## Important distinction (verified in codebase)

The existing `API_TRAFFIC_LOGGING` subsystem
(`src/main/java/com/znsio/teswiz/filters/apitraffic/` — `ApiTrafficLogging`,
`ApiTrafficLoggingFilter`, `ApiTrafficRecorder`, `ApiTrafficRecord`, `ApiCallContext`,
`ApiCallFileNamer`) captures **REST-Assured / Playwright API-client calls the test code
makes directly**. It is a global RestAssured `Filter`, writes one masked file per call into
the scenario folder, and reuses `SensitiveDataMasker`.

This feature is about the **browser's own XHR/fetch traffic** — a different capture layer.
To avoid confusion, propose a distinct property name: **`CAPTURE_WEB_API_TRAFFIC`**
(default `false`). It should reuse the `ApiTrafficRecorder` + scenario-folder +
`ScenarioArtifactReporter` publishing path and `SensitiveDataMasker` for consistency.

## Current state (verified in codebase)

- **Playwright-Java** already captures a HAR: `setRecordHarPath(harFile)` in
  `PlaywrightJavaDriverManager.buildContextOptions(...)`; also starts tracing. No
  structured/filterable request-response listeners yet.
- **Playwright-TS** already captures a HAR in `playwright/worker.mjs`
  (`contextOptions.recordHar = { path: harPath }`, ~line 597). No request/response events
  streamed back yet.
- **Selenium** captures no network traffic. No CDP/DevTools, no BrowserMobProxy anywhere.
- `WebCapability.NETWORK_INTERCEPTION`
  (`src/main/java/com/znsio/teswiz/web/WebCapability.java`) documents `page.route(...)` as
  the intended Playwright interception path, but it is not implemented.

## Mechanism per web engine

| Engine | Capture mechanism | Filtering (type / name / domain) | Status today |
|---|---|---|---|
| Playwright-Java | HAR already captured. Add `page.onRequest` / `page.onResponse` listeners for live, filterable capture; optionally `setRecordHarUrlFilter` | type → `request.resourceType()`; name → URL/path substring/glob; domain → host | HAR exists; filtered/structured capture is new |
| Playwright-TS | HAR already captured. Add request/response events in `worker.mjs`, stream summaries back over the worker protocol | Same as PW-Java, in the worker | New |
| Selenium | No native capture. CDP `Network.enable` + `Network.requestWillBeSent` / `responseReceived` (**Chromium only**), or a MITM proxy (BrowserMob / mitmproxy) for cross-browser + bodies | CDP event fields, or proxy HAR entries | Entirely new |

## Filtering design (type / name / domain)

- **type** → Playwright `resourceType` (xhr, fetch, document, script, image, …) or CDP
  `Network.ResourceType`.
- **name** → URL/path substring or glob.
- **domain** → host match.
- Config shape options: comma-separated include lists per dimension in properties, or a
  small JSON filter block in `browser_config.json`.
- Response **bodies** via CDP/Playwright require extra calls and may be large/binary —
  needs an explicit decision (size caps, binary handling).

## "Will app also support this?"

Not through this same mechanism. For `PLATFORM=android` / `iOS`, capturing the app's own
backend HTTP traffic needs a **proxy** (Appium has no built-in network sniffer):
BrowserMob/mitmproxy between device and backend, device trust of the proxy's TLS cert, and
(for real devices) network routing config. Feasible but materially heavier and different
from the browser path. **Recommended: scope app support as a separate follow-up TODO**, not
part of this feature.

## Shared work

1. New config property `CAPTURE_WEB_API_TRAFFIC` (default `false`):
   - Add to `configs/teswiz/teswiz_config.properties.template` **first**.
   - Add to every `configs/**/*.properties` (active or commented with default).
   - Consume in `Setup.java` with the standard boolean pattern; expose via `Runner`.
   - Add filter config (format TBD — see clarifications).
2. Route captured browser records through `ApiTrafficRecorder` and the scenario folder;
   mask with `SensitiveDataMasker`.
3. Register output in `ScenarioArtifactReporter` for auto-publishing.
4. Run `./gradlew validateConfigurationTemplates` after config changes.

## Pre-requisites

- Selenium path: Chromium-based browser for CDP, or a proxy dependency
  (BrowserMobProxy / mitmproxy) added to `build.gradle`.
- If capturing response bodies: agreement on size caps and binary handling.

4. Filter config **format**: comma-separated lists in properties, or a JSON block in

5. Output **format**: raw HAR, the existing per-call masked file style, or both?
6. Should **app (Android/iOS)** support be planned now as an explicit follow-up, or deferred
   entirely?

## Acceptance criteria (draft — finalize after clarifications)

- With `CAPTURE_WEB_API_TRAFFIC=true` and `PLATFORM=web`, browser XHR/fetch traffic is
  captured for each in-scope engine, filtered by configured type/name/domain, masked, and
  attached to the scenario report.
- With the property `false` (default), behaviour is unchanged and nothing is captured.
- `./gradlew validateConfigurationTemplates` and `./gradlew test` remain green.
